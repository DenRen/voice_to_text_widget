## Блок C. Кроссплатформенный tray/hotkey

### Вопрос 6. rumps + pystray + GTK

**Вердикт:** связка рабочая, но с оговорками. rumps жив, в режиме медленной поддержки,
на актуальной macOS (включая Apple Silicon) работает. pystray на Windows текст рядом
с иконкой показать **не может** — это ограничение самой Windows, а не библиотеки.
Единого кроссплатформенного tray-фреймворка с текстовым label на всех трёх ОС
к 2026 не появилось, потому что Windows его физически не поддерживает.

**Детали — rumps:**
- Последний релиз на PyPI — 0.4.0, обновляется редко, но проект не мёртв:
  мейнтейнер (@daredoes) ревьюит PR в свободное время, есть открытая работа
  над light/dark mode.
- Тонкая обёртка над PyObjC/NSStatusItem, поэтому почти не зависит от версии macOS.
  Сообщество подтверждает работу на Apple Silicon (проекты тестировались на
  M1/Monterey и M2/Ventura).
- **Бонус для VoiceTray:** `app.title` в rumps — это текст рядом с иконкой
  в menu bar, меняется динамически на лету (классический пример — Pomodoro-таймер,
  обновляющий title каждую секунду). Анимация уровня записи на macOS — тривиальна.

**Детали — pystray на Windows:**
- win32 — дефолтный бэкенд, «все фичи pystray» доступны, но это: иконка,
  tooltip (`title` в pystray = текст при наведении) и меню.
- Постоянного текста рядом с иконкой в Windows notification area не существует
  как концепции: tray — это Shell_NotifyIcon, иконка ~16×16, масштабируемая ОС.
- Стандартный обходной путь — рисовать текст/уровень **внутрь** самой иконки
  через PIL и присваивать `icon.icon = new_image` на лету; так делают
  CPU-индикаторы на pystray. Для анимации уровня записи работает, просто
  выглядит скромнее текста.

**Детали — единый фреймворк:**
- Tauri/tray-icon (tao/wry-биндинги) подтверждает картину на уровне нативных API:
  полноценный текстовый title у tray — фича, добавленная только для macOS
  (NSStatusItem); на Linux title не показывается без иконки; на Windows
  везде маппится в tooltip.
- Ваша архитектура «сменные tray-бэкенды» — правильная. *Моё мнение:*
  на Linux и Windows сразу закладывать «анимация = перерисовка иконки»,
  а текстовый label считать macOS-эксклюзивом.

**Ссылки:**
- https://github.com/jaredks/rumps
- https://pypi.org/project/rumps/
- https://pystray.readthedocs.io/en/latest/usage.html
- https://github.com/moses-palmer/pystray/issues/30 (динамическая иконка с текстом)
- https://v2.tauri.app/reference/javascript/api/namespacetray/ (платформенные ограничения title)
- https://github.com/tauri-apps/tao/commit/972307d (set_title — macOS-only фича)

### Вопрос 7. Глобальный хоткей на macOS для нетехнического пользователя

**Вердикт:** рекомендованный путь для инструкции — **Shortcuts.app** (встроен, GUI,
без стороннего софта), но с честным списком из трёх оговорок. skhd/Hammerspoon —
только fallback для тех, кто дружит с терминалом.

**Детали — Shortcuts.app (рекомендация):**
Схема: шорткат с действием «Run Shell Script» (`voice-tray --toggle`) →
в деталях шортката назначить клавиатурное сочетание.

Оговорки для инструкции:
1. «Run Shell Script» требует включить **Settings → Advanced → Allow Running
   Scripts** в настройках Shortcuts; бывают глюки с сохранением этой настройки
   (особенно на managed корпоративных маках).
2. Хоткеи шорткатов работают **только пока Shortcuts.app запущен** — добавить
   его в Login Items (окно можно закрыть, хоткеи продолжают работать).
3. Периодические «Operation not permitted» при запуске скриптов — лечится
   выдачей Full Disk Access.
4. Сочетание обязано включать модификатор (обычно Cmd); конфликты с системными
   хоткеями не детектируются. *Моё мнение:* в инструкции сразу предложить
   конкретное «безопасное» сочетание, например ⌃⌥⌘V.

**Детали — альтернативы:**
- **skhd**: идеален технически (биндинг «hotkey : shell command» одной строкой,
  hot-reload конфига), но требует Homebrew + Accessibility-разрешение,
  и основной репозиторий в maintenance mode (автор указывает на
  Zig-переписанный форк). Для нетехнического коллеги — нет.
- **Hammerspoon**: мощнее, но конфиг на Lua — тем более нет.
- **Karabiner**: ремаппер клавиш; для «хоткей → shell» избыточен и неудобен.

**Ссылки:**
- https://discussions.apple.com/thread/254878016 (хоткеи работают только при запущенном Shortcuts + Login Items)
- https://developer.apple.com/forums/thread/689436 (Allow Running Scripts и его глюки)
- https://discussions.apple.com/thread/255210852 (Operation not permitted → Full Disk Access)
- https://github.com/koekeishiya/skhd

## Блок D. Мелочи

### Вопрос 8. Метрика точности технических терминов

**Вердикт:** изобретать не нужно. Стандартный подход 2026 — обычный WER **плюс**
keyword-центричная метрика по списку своих терминов: Entity Error Rate
(1 − entity recall) или keyword precision/recall/F1 по выравниванию.

**Детали:**
- Проблема формализована в литературе: WER не отличает ошибку в ключевой
  сущности от ошибки в служебном слове. Свежие работы принимают **Entity Error
  Rate** — долю reference-сущностей, не распознанных целиком (сущность
  засчитывается только если все её слова без ошибок).
- Есть бенчмарк ровно вашего сценария (custom vocabulary): **Contextual
  Earnings-22** репортит WER + keyword precision/recall/F-score, где keyword —
  true positive только при точном совпадении текста и позиции по
  minimum-edit-distance выравниванию.
- В индустрии то же под именами Keyword Recall Rate / Missed Entity Rate;
  Pipecat выложил open-source STT-бенчмарк со стандартизованной Semantic WER;
  у AssemblyAI в benchmarking SDK есть генерация semantic word lists из данных.
- *Моё мнение (практика):* для вашего размера задачи достаточно `jiwer` для WER
  + ~50 строк своего кода: список терминов → выравнивание hypothesis/reference
  по edit distance → recall терминов. Готовые тулзы делают ровно это,
  а список терминов у вас всё равно свой.

**Ссылки:**
- https://arxiv.org/pdf/2604.00610 (Entity Error Rate)
- https://arxiv.org/pdf/2604.07354 (Contextual Earnings-22: keyword P/R/F по выравниванию)
- https://www.assemblyai.com/blog/word-error-rate-is-broken (обзор метрик, Pipecat/Semantic WER)

### Вопрос 9. `uv tool install` из приватного git

**Вердикт:** работает штатно. Главные грабли — аутентификация при **обновлениях**
и синтаксис extras в URL.

**Детали:**
- **Аутентификация:** uv поддерживает SSH (`git+ssh://git@host/...`, username
  обязательно `git`) и HTTPS с токеном (`git+https://<user>:<token>@host/...`;
  для GitHub PAT username произвольный). Если кредов в URL нет, uv спрашивает
  git credential helper. Для разработчиков проще SSH (ключ и так настроен);
  для нетехнических — PAT через credential helper, а не в URL (чтобы токен
  не осел в истории shell).
- **Обновления:** `uv tool upgrade voice-tray` перезапрашивает git, т.е.
  аутентификация нужна каждый раз — протухший токен = молчаливое падение
  с git-ошибкой. uv кэширует git-зависимости по полностью разрешённому commit
  hash, поэтому «поставил вчера, новых коммитов не видит» решается именно
  `uv tool upgrade`, а не повторным install.
- **Extras:** `uv tool install "voice-tray[local] @ git+ssh://git@host/repo.git"` —
  работает, но кавычки обязательны (скобки съедает shell). *Моё мнение:*
  прописать явно в README, коллеги на этом спотыкаются.
- **Self-hosted GitLab:** клон по git+ssh падает с «Host key verification
  failed», если хост не в known_hosts; лечится одним `ssh-keyscan -H <host>
  >> ~/.ssh/known_hosts` или первым ручным `git clone`.

**Ссылки:**
- https://docs.astral.sh/uv/concepts/authentication/git/
- https://github.com/astral-sh/uv/issues/18005 (host key verification на self-hosted GitLab)

## Что я бы поменял в ваших решениях (по итогам блоков C/D)

Архитектурно всё подтверждается, две правки:

1. В спеке tray-абстракции явно зафиксировать: «текст рядом с иконкой» есть
   только на macOS, а Linux/Windows-бэкенды обязаны уметь рендерить состояние
   в саму иконку. Иначе интерфейс бэкенда получится macOS-центричным
   и его придётся ломать.
2. В инструкции для macOS-коллег не давать выбор из четырёх утилит, а дать
   один путь через Shortcuts.app с тремя known issues (Allow Running Scripts,
   Login Items, Full Disk Access). *Моё мнение*, но source-backed оговорки
   выше показывают, что без них инструкция «не заведётся» у половины людей.
