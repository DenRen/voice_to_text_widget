# Трек 3. Всегда локально + почти нулевая латентность

> Цель: (а) локальный режим становится режимом по умолчанию, звук никогда не
> покидает машину; (б) задержка между «нажал стоп» и «текст в клипборде» —
> субсекундная, вместо нынешних десятков секунд на длинных диктовках.
> Статус (2026-08-17): **реализовано** в `local_asr.py` — но не по LocalAgreement, а
> проще: транскрипция окнами ≤30 с, нарезанными по паузам, во время записи; после
> «стоп» остаётся один хвост. Замеры на i7-1355U показали, что стоимость окна — это
> почти целиком энкодер (~4–6 с на 30-с окно с паддингом, декод <1 с), а без паддинга
> Whisper на русском разваливается (WER 0.8–1.8), поэтому перепрогоны по растущему
> буферу (LocalAgreement) на CPU нереальны и не нужны. Плюс `cpu_threads` = число
> физических ядер (дефолт CT2 = 4 потока был ~2× медленнее) и warm-up. Итог:
> ожидание после «стоп» ~5–7 с независимо от длины (было ~10 с за каждые 30 с речи).

## 1. Откуда берётся текущая латентность

Сейчас пайплайн строго последовательный:

```
запись N секунд → stop → WAV на диск → transcribe(весь файл) → clipboard
                         └────────── всё ожидание здесь ──────────┘
```

Модель уже резидентна в памяти (загружается при старте — хорошо), поэтому
ожидание ≈ `RTF × N`, где RTF (real-time factor) — скорость модели
относительно реального времени. На нашем железе (i7-1355U, 2P+8E ядер, без
дискретного GPU) для `large-v3-turbo` int8 RTF предположительно 0.3–0.7
(**надо замерить, а не гадать** — см. §5 Фаза 0). То есть минутная диктовка =
20–40 секунд ожидания. Чем длиннее диктовка, тем хуже — линейно.

## 2. Ключевая идея: транскрибировать ВО ВРЕМЯ записи

Идея автора — «бить аудиозапись на куски и гонять модель по кускам, пока я
ещё говорю» — это ровно **streaming ASR**, стандартная и хорошо изученная
техника. Опасение «слова первой секунды могут зависеть от последней секунды»
справедливо, но решено в литературе:

- Зависимость контекста в речи **локальна** — на практике несколько секунд,
  а не вся минута. Whisper в любом случае видит окно максимум 30 секунд.
- Алгоритм **LocalAgreement-2** ([ufal/whisper_streaming](https://github.com/ufal/whisper_streaming)):
  модель прогоняется по растущему буферу каждые ~1 с; **коммитится только
  стабильный префикс** — та часть текста, которая совпала в двух
  последовательных прогонах. Хвост остаётся «плавающим» и может меняться,
  пока не стабилизируется. Опубликованная латентность — ~3.3 с на потоке;
  для нашего кейса важнее другое: к моменту нажатия «стоп» почти вся диктовка
  уже транскрибирована.

```
запись:      ████████████████████████████████░ stop
транскрипция: └─┬─┘└─┬─┘└─┬─┘ ... (инкрементально, параллельно записи)
committed:      ██████████████████████████░░
                                          └ хвост 1–3 с — дотранскрибировать
ожидание после stop ≈ RTF × 3 с  ≈  ~1 секунда
```

Дополнительно — **VAD-сегментация** (Silero VAD, уже используется внутри
faster-whisper как `vad_filter=True`): паузы в речи дают естественные границы
чанков, где «зависимость от будущего» нулевая, и там префикс коммитится сразу.

### Цена: CPU во время записи

Инкрементальные прогоны означают, что CPU занят всё время диктовки, а не
только после. На ноуте от батареи это заметно. Митигации:
- прогон не чаще раза в 1–2 с и только по некоммиченному хвосту + контекст;
- VAD-gating: в тишине модель не дёргаем вообще;
- модель поменьше для стриминга (см. §4) — и это же снижает латентность хвоста.

### Реализация: своя или готовая?

Кандидаты: [ufal/whisper_streaming](https://github.com/ufal/whisper_streaming)
(референс LocalAgreement), [WhisperLive](https://github.com/collabora/WhisperLive)
(клиент-сервер, для нас оверкилл), WhisperLiveKit (сервер + диаризация, оверкилл).
**Рекомендация**: взять из whisper_streaming сам алгоритм (ядро LocalAgreement —
~100–200 строк) и реализовать у себя как `transcribe/fw_streaming.py` поверх
уже используемого faster-whisper. Серверные обвязки не тащим: наш кейс —
локальный однопользовательский виджет, а не сервис.

## 3. «Всегда локально» — смена дефолта

- `--local` перестаёт быть флагом: **локальный режим становится дефолтом**.
- Groq остаётся как opt-in `--cloud` (legacy) либо выпиливается совсем —
  решить при реализации. Для коллег дефолт «ничего не уходит с машины»
  обязателен: не у всех есть GROQ_API_KEY, и не все имеют право отправлять
  рабочие диктовки наружу.
- Побочный бонус: исчезает ограничение Groq в 30 секунд на запрос.
- Первый запуск качает модель один раз (сейчас ~1.5 GB для turbo); дальше
  `local_files_only=True`. Для оффлайн-инсталляций описать в README перенос
  кэша `~/.cache/huggingface` руками.

## 4. Выбор модели: не только Whisper

Наш профиль нагрузки: русская речь с вкраплениями английских технических
терминов (см. `~/.voice_to_text/prompt.txt`), CPU-only x86 ноутбук.

| Кандидат | Плюсы | Минусы / риски |
|---|---|---|
| **faster-whisper large-v3-turbo int8** (сейчас) | качество проверено на себе; `initial_prompt` подхватывает наши термины; мультиязычность = code-switching из коробки | 809M параметров — самый медленный из кандидатов на CPU |
| **faster-whisper small/medium int8** | 2–5× быстрее | заметная деградация на русском с терминами — проверить бенчмарком |
| **[GigaAM-v3](https://github.com/salute-developers/GigaAM)** (Сбер, MIT, 220–240M, Conformer CTC/RNNT) | SOTA на русском (заявлено 70:30 против whisper-large-v3); в ~4 раза меньше turbo → ожидаемо сильно быстрее на CPU; e2e-вариант умеет пунктуацию; ONNX: [onnx-asr](https://pypi.org/project/onnx-asr/) / [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) | **главный риск — английские термины в русской речи**: модель русскоцентрична, механизма prompt/словаря нет; пунктуация вне e2e-варианта; проверить бенчмарком на своих записях |
| whisper.cpp (Vulkan/SYCL на Intel iGPU Iris Xe) | задействует простаивающий iGPU | отдельный рантайм; выигрыш на iGPU против 10 CPU-ядер не очевиден — только по результатам замера |
| Vosk (streaming, ru-модель) | по-настоящему стриминговый, очень лёгкий | качество ощутимо ниже всех кандидатов — рассматривать только как fallback для слабых машин |

Возможная гибридная схема, если GigaAM провалит термины, а turbo окажется
медленным: **two-pass** — лёгкая модель стримит черновик в реальном времени,
большая перепроверяет финальный текст после стопа (пользователь может вставить
черновик сразу, а через пару секунд в клипборде появляется уточнённая версия).
Усложнение заметное — только если одномодельные варианты не дотянут.

## 5. План реализации

### Фаза 0 — бенчмарк-харнесс (без него решения не принимаем)

Собрать 15–30 реальных диктовок автора (WAV + эталонный текст; сырьё для
эталонов уже есть — `~/.voice_to_text/transcriptions.log` и возможность
записать свежие сэмплы самой тулой). Обязательно включить сэмплы с плотными
английскими терминами. Скрипт меряет по каждой связке модель×параметры:

- **WER/CER** на русском тексте — готовой библиотекой `jiwer`;
- **отдельно точность технических терминов** — по итогам веб-ресёрча
  изобретать не надо: стандартный подход — keyword recall / Entity Error
  Rate (термин засчитан, только если все его слова распознаны точно, при
  выравнивании hypothesis/reference по edit distance). Готовые тулзы
  заточены под свои словари, поэтому пишем ~50 строк своего кода поверх
  выравнивания + список терминов из `prompt.txt`. Референсы: keyword
  precision/recall/F1 в бенчмарке Contextual Earnings-22, Entity Error Rate
  в свежих ASR-работах, разбор «чем плох голый WER» у
  [AssemblyAI](https://www.assemblyai.com/blog/word-error-rate-is-broken);
- **RTF** на нашем CPU;
- пиковая RAM.

Матрица: {turbo, medium, small} × {int8} × {beam 1, beam 5} + GigaAM-v3 (CTC и
e2e) + whisper.cpp/iGPU (опционально). Результаты — таблицей в
`docs/design/benchmarks.md`.

### Фаза 1 — быстрые победы (дни, без стриминга)

Снижают латентность в разы уже сейчас:
- `beam_size=1` (greedy) вместо 5 — типично 2–3× быстрее; деградацию качества
  ловим бенчмарком;
- `cpu_threads` под нашу топологию (2P+8E) — подобрать замером;
- `BatchedInferencePipeline` из faster-whisper — на записях длиннее ~30 с
  даёт кратное ускорение за счёт батчинга VAD-сегментов;
- warm-up прогон 1 с тишины при старте (первый инференс всегда медленнее);
- по итогам бенчмарка — возможно, смена модели по умолчанию.

### Фаза 2 — стриминг (главное блюдо)

1. Запись переезжает на ring buffer (синергия с миграцией на sounddevice
   из трека 1).
2. `transcribe/fw_streaming.py`: инкрементальные прогоны + LocalAgreement-2 +
   VAD-gating (см. §2).
3. UI: в tray-label к анимации уровня добавляется индикация «сколько уже
   закоммичено» (например `🔒🎤●●● 47w`), чтобы было видно, что стриминг живёт.
4. После стопа — финализация хвоста и клипборд. Целевая метрика:
   **p95 задержки stop→clipboard < 1.5 с** на минутной диктовке.

### Фаза 3 — альтернативный движок (по итогам Фазы 0)

Если GigaAM-v3 выигрывает бенчмарк с приемлемыми терминами — добавить
`transcribe/gigaam.py` (через onnx-asr; сам инференс ~10 строк) и сделать её
дефолтом для русского профиля. Архитектура из
[00-overview.md](00-overview.md) делает это заменой одного бэкенда.

## 6. Открытые вопросы

- [ ] Реальный RTF всех кандидатов на i7-1355U — только замер (Фаза 0).
- [ ] GigaAM-v3 и code-switching (английские термины в русской речи) — главный
  риск альтернативы, проверяется бенчмарком; поискать чужие отчёты (веб-ресёрч).
- [ ] Насколько LocalAgreement дружит с диктовкой «с паузами на подумать»
  (наш режим — не непрерывная лекция): не будет ли лишних перезапусков контекста.
- [ ] Стриминг + prompt: у whisper_streaming `initial_prompt` применяется к
  каждому окну — проверить, не деградирует ли поведение наших терминов.
- [ ] Энергопотребление стриминга от батареи — замерить, возможно сделать
  стриминг отключаемым (`--no-streaming` → старое поведение).
